# Docker Compose Deployment

This guide walks through deploying StackWeaver using Docker Compose on a single machine.
This is the quickest way to get started for development, evaluation, or small-scale production use.

## Prerequisites

You need the following installed on your host machine.

- Docker Engine 24+ with Docker Compose v2
- Git
- At least 4 GB of free RAM (8 GB recommended)
- Ports 5173 (frontend), 8022 (API), and 8080 (Zitadel) available

## Quick Start

Clone the repository and start all services with a single command.

```bash
git clone https://github.com/stackweaver/stackweaver.git
cd stackweaver
make up
```

This starts all services (PostgreSQL, Redis, MinIO, Zitadel, the API, frontend, orchestrator, runners) using Docker Compose with `network_mode: host`.
The first run takes a few minutes while containers are built and Zitadel initialises.

Once everything is running, open `http://localhost:5173` in your browser.
The default Zitadel admin credentials are `admin@ZITADEL.localhost` / `Password1!`.

## Architecture

All services run on the host network (`network_mode: host`), so they communicate via `localhost` on their respective ports.

| Service | Port | Description |
|---|---|---|
| Frontend | 5173 | React SPA (Vite dev server) |
| API | 8022 | Go REST API |
| Zitadel | 8080 | OIDC identity provider |
| Login UI | 3000 | Zitadel login interface |
| PostgreSQL | 5432 | Database |
| Redis | 6379 | Job queue and pubsub |
| MinIO | 9000 | Object storage (state, configs, registry) |
| MinIO Console | 9001 | MinIO web UI |

The orchestrator, Terraform runner, and Ansible runner do not expose ports — they communicate via the Redis queue and PostgreSQL.

## Service Management

```bash
make up              # Start all services
make down            # Stop all services (preserves data)
make fresh           # Rebuild and restart code containers (keeps infra)
make fresh-backend   # Rebuild and restart API container only
make fresh-frontend  # Rebuild and restart frontend container only
make restage         # Full cleanup and fresh start (removes volumes, rebuilds)
make clean           # Remove containers AND volumes (destroys all data)
```

View logs for a specific service.

```bash
docker compose -f deploy/docker-compose.yml logs api          # API logs
docker compose -f deploy/docker-compose.yml logs orchestrator  # Orchestrator logs
docker compose -f deploy/docker-compose.yml logs runner        # Runner logs
docker compose -f deploy/docker-compose.yml logs zitadel       # Zitadel logs
docker compose -f deploy/docker-compose.yml logs zitadel-init  # Init logs (credentials)
```

## Configuration

### Environment Files

StackWeaver uses several environment files in the `deploy/` directory.
Most credentials are auto-generated by the `zitadel-init` container on first startup.

| File | Purpose | How to edit |
|---|---|---|
| `deploy/.env` | Auto-generated credentials (Zitadel client IDs, tokens) | **Do not edit** — overwritten by `zitadel-init` |
| `deploy/sso.env` | SSO / external IdP credentials | Copy from `sso.env.example`, edit manually |
| `deploy/vcs.env` | VCS provider OAuth credentials | Copy from `vcs.env.example`, edit manually |
| `deploy/oidc.env` | OIDC workload identity signing key | Copy from `oidc.env.example`, edit manually |

To enable a VCS integration (e.g. GitHub App), edit `deploy/vcs.env`.

```bash
cp deploy/vcs.env.example deploy/vcs.env
# Edit deploy/vcs.env with your values
make fresh-backend
```

For a full list of every environment variable, see the [Environment Variables Reference](environment-variables.md).

### Custom Domain (Production)

By default StackWeaver runs on `localhost`.
To use a custom domain, Zitadel's external domain configuration must be updated.

1. Edit `deploy/zitadel-defaults.yaml` and set the `ExternalDomain`, `ExternalPort`, and `ExternalSecure` fields.
2. Set the `ZITADEL_CUSTOM_DOMAINS` environment variable in `deploy/zitadel-init.yaml` or directly as an env var.
3. Update frontend env vars to point to the new domain.

See the [Zitadel Setup guide](ZITADEL_SETUP.md) for detailed instructions.

### Reverse Proxy

For production deployments behind a reverse proxy (nginx, Caddy, Cloudflare Tunnel), you need to route two domains.

**App domain** (e.g. `app.example.com`):
- `/api/v2/*`, `/.well-known/terraform.json`, `/v1/modules/*`, `/health` → `localhost:8022`
- Everything else → `localhost:5173`

**Auth domain** (e.g. `auth.example.com`):
- `/ui/v2/login/*` → `localhost:3000`
- Everything else → `localhost:8080`

A Cloudflare Tunnel example is provided in `deploy/cloudflared-config.example.yml`.

## Data Persistence

Docker Compose uses named volumes for persistent data.

| Volume | Data | Critical? |
|---|---|---|
| `postgres_data` | Database (all application state) | Yes — back up regularly |
| `minio_data` | Object storage (Terraform state, configs, registry) | Yes — back up regularly |
| `runner-workspaces` | Temporary workspace files | No — recreated on runs |
| `zitadel-pat` | Zitadel admin PAT (shared with init job) | No — regenerated on init |

To back up PostgreSQL, use `pg_dump`.

```bash
docker exec postgres pg_dump -U iac iac_platform > backup.sql
```

## Upgrading

Pull the latest code and rebuild.

```bash
git pull
make fresh
```

The API auto-migrates the database schema on startup via GORM, so no manual migration step is needed.
If a release includes breaking changes, the release notes will contain specific upgrade instructions.

## Troubleshooting

**Services fail to start**: Check that all required ports are free. `ss -tlnp | grep -E '5173|8022|8080|5432|6379|9000'` shows any conflicts.

**Zitadel init fails**: The `zitadel-init` container needs Zitadel to be fully ready. Check `docker compose -f deploy/docker-compose.yml logs zitadel-init` and restart it with `docker compose -f deploy/docker-compose.yml restart zitadel-init`.

**API can't connect to database**: Ensure PostgreSQL is healthy. `docker compose -f deploy/docker-compose.yml ps postgres` should show `healthy`. Check that the database credentials in `config.yaml` match the PostgreSQL container environment.

**Frontend shows blank page**: Check browser console for CORS errors. Ensure `VITE_API_URL` and `VITE_ZITADEL_ISSUER` are set correctly. In Docker Compose development mode these are Vite build-time variables; rebuilding is required after changes (`make fresh-frontend`). In Kubernetes, they are injected at runtime via `env.js` — no rebuild needed, just run `helm upgrade`.
