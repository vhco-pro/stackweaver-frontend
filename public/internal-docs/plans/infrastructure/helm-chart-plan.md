# Helm Chart for StackWeaver — Plan

**Status:** ✅ Substantially implemented — `deploy/helm/stackweaver/` exists with templates for all services (API, frontend, orchestrator, runners, PostgreSQL, Redis, MinIO, Zitadel). Verify completeness against `values.yaml`.

## Overview

Provide an official Helm chart in `deploy/helm/stackweaver/` so operators can run StackWeaver on Kubernetes. The chart bundles optional dependencies for a quick all-in-one install, while supporting "bring your own" instances for PostgreSQL, Redis, object storage, and Zitadel.

**Key design decisions (updated 2026-02):**
- **In-chart manifests** for all deps — full control, no subchart version coupling.
- **Two-domain ingress**: `app` domain (frontend + API via path routing) and `auth` subdomain (Zitadel + Login UI).
- **Auto-generated secrets by default** — chart creates Secrets with random values when `secretName` is empty. Uses Helm `lookup` to preserve values across upgrades and `helm.sh/resource-policy: keep` to survive uninstalls.
- **External secrets for GitOps** — when `secrets.*.secretName` is set, the chart creates zero Secret resources. All rendered manifests are safe for Git.
- **No ConfigMap + init-container substitution** — env vars are set directly on containers, keeping deployments simple.
- **Frontend runtime config via env.js** — generic frontend image with domain-specific values injected at deploy time from a ConfigMap. Zitadel client ID injected from secret by init container.
- **Env var overrides in Go backend** — API, orchestrator, and runner binaries support overriding config.yaml values via environment variables.
- **Zitadel is REQUIRED** — `zitadel.bundled` toggles between in-chart and external Zitadel, not optional/off.
- **Zitadel PAT sharing** via a PVC between the Zitadel Deployment and zitadel-init Job.
- **Minimal ConfigMaps** — only used for values that genuinely cannot be env vars (Zitadel YAML config, frontend env.js). All passwords via env vars from Secrets.

## Secrets Architecture

The chart supports two modes: auto-generated (default) and external (GitOps).

### Auto-Generated Secrets (Default)

When `secrets.<component>.secretName` is empty, the chart creates a Secret with random values.

```yaml
# templates/secrets-autogenerated.yaml creates:
# 1. <release>-postgresql    — random 24-char password
# 2. <release>-minio         — minioadmin + random 32-char secret
# 3. <release>-encryption    — 64-char hex key (sha256sum of random data)
# 4. <release>-zitadel       — 32-char masterkey + complex password + empty placeholder keys
```

Key implementation details:
- **Helm `lookup` function** checks if the Secret already exists in the cluster before generating new random values. This prevents credentials from changing on every `helm upgrade`.
- **`helm.sh/resource-policy: keep` annotation** prevents Helm from deleting the Secret on `helm uninstall`, protecting generated credentials.
- The `_helpers.tpl` helpers default to `<fullname>-<component>` when `secretName` is empty (no longer uses `required`).

### External Secrets (GitOps-Safe)

When `secrets.<component>.secretName` is set, the chart uses that pre-existing Secret and creates no Secret resources.

```yaml
secrets:
  postgresql:
    secretName: my-db-secret          # Chart creates zero Secrets
    keys:
      password: password              # Customisable key names
  minio:
    secretName: my-minio-secret
  encryption:
    secretName: my-enc-secret
  zitadel:
    secretName: my-zitadel-secret
```

## Frontend Runtime Configuration

The frontend image is generic — no VITE_* build args are baked in.

### How it works

1. **ConfigMap** (`configmap-frontend.yaml`) generates `env.js` with domain-specific values derived from Helm ingress hosts:
   - `VITE_API_URL` from `ingress.hosts.app`
   - `VITE_ZITADEL_ISSUER` from `ingress.hosts.auth`
   - `VITE_ZITADEL_REDIRECT_URI` from `ingress.hosts.app`

2. **Init container** (busybox) in the frontend Deployment:
   - Copies `env.js` from ConfigMap to an emptyDir
   - Uses `sed` to inject `VITE_ZITADEL_CLIENT_ID` from the Zitadel secret (since ConfigMaps cannot reference Secrets)

3. **Frontend container** mounts the emptyDir at `/usr/share/nginx/html/env.js`

4. **`index.html`** loads `<script src="/env.js">` with an onerror fallback for dev mode

5. **`src/config.ts`** reads `window.__STACKWEAVER__` → `import.meta.env` → defaults

### Why this pattern?

- Same image for dev/staging/production
- No image rebuild when changing domains
- Zitadel client ID (from Secret) cannot go in a ConfigMap, hence the init container
- Graceful fallback to Vite build-time vars for local development

## Environment Variable Strategy

Each container gets its environment variables directly from the Deployment spec. Shared env var blocks (database, redis, storage, encryption) are defined as template snippets in `_helpers.tpl`:

- `stackweaver.env.database` — DATABASE_HOST, DATABASE_PORT, DATABASE_USER, DATABASE_PASSWORD, DATABASE_NAME, DATABASE_SSLMODE
- `stackweaver.env.redis` — REDIS_HOST, REDIS_PORT, REDIS_PASSWORD, REDIS_DB
- `stackweaver.env.storage` — STORAGE_ENDPOINT, STORAGE_ACCESS_KEY, STORAGE_SECRET_KEY, STORAGE_USE_SSL
- `stackweaver.env.encryption` — ENCRYPTION_KEY

Every component also accepts an `env: {}` map in values.yaml for user-provided overrides. These are rendered last and take precedence.

### Go Backend Changes

Three binaries were modified to support env var overrides:

- **API** (`cmd/api/main.go`): `applyEnvOverrides()` function overrides config.yaml values for SERVER_HOST, SERVER_PORT, DATABASE_*, ZITADEL_ISSUER, ZITADEL_API_CLIENT_ID, ZITADEL_API_CLIENT_SECRET.
- **Orchestrator** (`cmd/orchestrator/main.go`): `getEnv()`/`getEnvInt()` helpers replace previously hardcoded `localhost` Redis/database connections.
- **Runner** (`cmd/runner/main.go`): Same pattern — all Redis, database, and MinIO connections now read from env vars with sensible defaults.
- **Ansible Runner**: Already used env vars natively — no changes needed.

## Ingress Strategy

Two-domain layout — configurable via `ingress.hosts.app` and `ingress.hosts.auth`:

**App domain** (`stackweaver.example.com`):
- `/api/v2/*` → API service (port 8022)
- `/.well-known/terraform.json` → API service (Terraform service discovery)
- `/v1/modules/*` → API service (module registry)
- `/health` → API service (monitoring)
- `/*` → Frontend service (port 80, nginx SPA)

**Auth domain** (`auth.stackweaver.example.com`):
- `/ui/v2/login/*` → Login UI service (port 3000)
- `/*` → Zitadel service (port 8080, OIDC endpoints)

TLS: ingress-level termination via cert-manager or pre-provisioned Secrets.

## Init and Ordering

- **PostgreSQL** — `init-postgres.sql` (uuid-ossp extension + zitadel database creation) as ConfigMap.
- **MinIO** — Bucket-init Job creates `iac-state`, `terraform-registry`, `ansible-artifacts` after MinIO is healthy.
- **Zitadel** — When bundled:
  1. Zitadel Deployment starts with `start-from-init`. DB passwords injected via `ZITADEL_DATABASE_POSTGRES_*` env vars (not in ConfigMap). Admin password via `ZITADEL_FIRSTINSTANCE_ORG_HUMAN_PASSWORD`.
  2. `zitadel-init` Job (post-install and post-upgrade hook) creates org, project, OIDC apps, service users.
  3. Init job patches the Zitadel K8s Secret directly via in-cluster API calls (dedicated ServiceAccount + Role), then triggers rolling restarts of the API, frontend, and login-ui. No manual steps required.
